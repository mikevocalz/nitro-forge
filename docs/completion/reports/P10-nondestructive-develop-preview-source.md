# P10 non-destructive develop recipe and real preview processing

Added a persistent Develop schema 1 per photo version and actual bounded RGBA processing. This extends the catalog with working pixel operations; it is not a RAW decoder, durable original store, ICC engine or complete RAWDevelopPanel backend.

Recipe: exposure_ev −8..8, contrast 0..4 and three RGB gains 0..8, all finite. Identity is 0 EV, contrast 1 and gains [1,1,1]. Each version defaults to identity; identity recipes are omitted from snapshot encoding so prior catalog snapshots remain backward compatible and retain their byte representation. Changed recipes persist with the existing validated catalog state/Arc history; noops preserve redo. ReadDevelop returns explicit settings even when the snapshot omits identity defaults.

The processor accepts declared `rgba8-straight-srgb` packed bytes. Its sRGB transfer functions follow [W3C CSS Color4 color conversion sample code](https://www.w3.org/TR/2026/CRD-css-color-4-20261103/#color-conversion-code): decode to linear light, multiply by 2^exposure_ev and each channel gain, apply `(linear−0.18)×contrast+0.18`, clip 0..1, encode to sRGB and round to nearest 8-bit value. The fixed contrast pivot is a declared operator choice, not an ICC/profile or photographic-calibration claim. Alpha bytes remain exact, including alpha 0; hidden RGB still receives the color transform. Identity returns input bytes exactly. No Kelvin/temperature/tint, lens, tone curves, masking, local edits, mixer or HDR capability is implied.

ProcessPreview requires version_id, original_id, original_sha256 and expected_develop to match current authoritative catalog data before processing. It rejects stale recipes and mismatched identities. The source hash is a host/provider assertion tying the job to the immutable descriptor, not proof that RGBA pixels were decoded from that RAW original. The host still owns verified original storage, decoder provenance and generation admission.

Inputs cap at 4096 per side and 1048576 pixels, exactly width×height×4 bytes; binary/base64 sizes are preflighted before decode/processing allocation. Output is real processed RGBA with matching identity/recipe/format/stride metadata. Processing is read-only and creates no journal entry or persistent pixel cache. Native Command.input moves owned bytes and may return binary output; the existing JSON-only DocumentHandle/EngineHost uses a bounded immediate base64 facade. That facade copies the exact Uint8Array/Buffer view and recipe before awaits, validates response identity/recipe/dimensions and preflights encoded output length before allocating its decoded buffer. No optional/fake native host shim was added.

Long processing checks cancellation every 4096 pixels and again after output encoding before publication, reporting progress from actual processed pixel count. Cancellation cannot mutate catalog settings because this operation is read-only. Pre-cancel behavior is tested; a native task/platform cancellation matrix was not run. Logical pixel/state limits are not a measured RSS claim; floating-point output has not been accepted across every platform/libm build.
